Section 1

Executive Summary

AegisAI is a demonstration platform built to illustrate how a unified, rule-based security policy engine can be applied to AI-driven interactions. It targets two primary attack surfaces: AI chatbot prompts and autonomous AI agent actions. The platform provides real-time policy evaluation, sensitive data scanning and redaction, component trust-relationship visualisation, and aggregated analytics — all within a single Streamlit dashboard.

The project is implemented entirely in Python using Streamlit, pandas, Plotly, and pyvis. All data is simulated; no real AI models, external APIs, or databases are used. AegisAI serves as a teaching and prototyping tool for AI security concepts, demonstrating how detection logic, trust modelling, and policy enforcement can be layered together.

Section 2

Problem Statement

As AI chatbots and autonomous agents are deployed in more enterprise and consumer settings, they introduce attack surfaces that traditional security tooling was not designed to address. Key threats include:

  • Prompt Injection & Jailbreaking — Malicious inputs crafted to override an AI model's instructions or safety guidelines.
  • Sensitive Information Extraction — Prompts designed to make the AI reveal its system prompt, internal configuration, or confidential data.
  • Unauthorised Resource Access — Agents autonomously accessing files, databases, or tools they have not been granted permission to use.
  • Uncontrolled Data Transfers — Agents sending data to unapproved external endpoints, risking exfiltration.
  • Credential Exposure — API keys, passwords, and tokens inadvertently included in prompts or agent outputs.
  • Reconnaissance Attempts — Queries intended to enumerate internal users, systems, or data structures.

Most existing security products focus on network traffic, application logs, or code vulnerabilities. They do not inspect the semantic content of AI prompts and responses, nor do they model the trust boundaries between AI components. AegisAI demonstrates how these gaps can be addressed with a lightweight, rule-based policy layer.

Project Objectives

  • Show how sensitive-data detection and redaction can be integrated into an AI processing pipeline.
  • Visualise component trust relationships and permission boundaries using an interactive graph model.
  • Provide an interactive Security Playground for testing and demonstrating policy rules in real time.

Section 6

Security Detection Engine & Rule Set

The core detection function evaluate_security_event() evaluates a single event against an ordered set of rules. Rules are applied in priority sequence — once a BLOCK decision is set, no lower-priority rule can downgrade it.

Priority map: BLOCK (2) > FLAG (1) > ALLOW (0)

RuleTrigger ConditionDecisionRisk
Rule C AI Agent + resource not on approved list BLOCK HIGH
Rule E AI Agent + destination not on approved list BLOCK HIGH
Rule G (unapproved) AI Agent + sensitive data + unapproved destination BLOCK HIGH
Rule G (approved) AI Agent + sensitive data + approved destination FLAG HIGH
Rule D Simulated API key / credential pattern in text FLAG HIGH
Rule B — Jailbreak Jailbreak phrase detected in prompt BLOCK HIGH
Rule B — Extraction System-prompt extraction phrase detected FLAG HIGH
Rule B — Recon Enumeration / reconnaissance phrase detected FLAG MEDIUM
Rule B — Sensitive Sensitive data explicitly flagged in context FLAG MEDIUM
Rule F AI Agent — all checks pass ALLOW LOW
Rule A Chatbot — all checks pass (default) ALLOW LOW

Detection Phrase Lists (v1.1)

The engine maintains three phrase lists used in Rule B. All lists were significantly expanded in v1.1 to cover more attack patterns while maintaining zero false positives on benign educational queries.

ListCountDecisionExample phrases
_JAILBREAK_PHRASES 45+ BLOCK "ignore all previous instructions", "ignore previous instructions and", "dan mode", "act without restrictions", "bypass your safety rules", "output all passwords", "disregard your guidelines and", "forget all your instructions"
_EXTRACTION_PHRASES 70+ FLAG "reveal the confidential system prompt", "reveal all stored passwords", "show me all api keys", "bypass access controls", "circumvent the access controls", "send confidential", "disclose all credentials", "give me the api key"
_RECON_PHRASES 18+ FLAG "enumerate all users", "list all accounts", "dump the database", "give me all usernames", "map access levels", "show all users"
Design principle: Phrase lists match imperative requests targeting protected values. Benign educational questions such as "How should developers store API keys securely?" or "Explain what a system prompt is" do not match — they contain no action verb directed at exposing a value.

Rule D additionally uses a compiled regex (_SECRET_PATTERN) to detect patterns resembling OpenAI-style API keys (sk-...), AWS-style keys (AKIA...), password-like strings (p@ssw...), and labelled dummy secrets.

Section 7

Sensitive Data Detection and Redaction

detect_sensitive_data(text) applies six compiled regular expressions to the input text. Matched values are replaced in-place with labelled placeholders. The original matched values are never stored in the event log — log_event() always stores the redacted copy.

CategoryPattern ApproachRedaction Placeholder
Email AddressRFC-like user@domain.tld[REDACTED EMAIL]
Phone NumberUS 10-digit with optional country code[REDACTED PHONE]
Password Assignmentpassword=... / passwd:... + 4+ char value[REDACTED PASSWORD]
API Key / Credentialsk-... (OpenAI-style), AKIA... (AWS-style), api_key=...[REDACTED API KEY]
Secret / Tokensecret=..., bearer=..., auth_token=...[REDACTED SECRET]
Credit Card PatternFour groups of four digits[REDACTED CARD NUMBER]
Limitation: Pattern-based detection can produce false positives (ordinary text matching a pattern) and false negatives (sensitive data in an unrecognised format). This tool should not be relied upon as the sole detection mechanism in a production system.

When the Unified Policy Engine runs, it always performs the sensitive data scan first (Step 1) and passes the redacted copy of the description to the core security engine (Step 2). This ensures that even if a credential bypasses Rule D, it is never stored in plain text.

Section 9

Analytics and Evaluation Lab

Analytics Dashboard

_build_analytics_df() merges three session-state sources (security_log, evaluated_df, raw events_df) into a single normalised DataFrame used for all charts and KPI computation.

Four Plotly charts are rendered:

  • Decision Distribution — Donut chart of ALLOW / FLAG / BLOCK counts
  • Risk Level Distribution — Donut chart of Low / Medium / High counts
  • Events by Component — Stacked bar chart: Chatbot vs AI Agent, coloured by decision
  • Top Rules Triggered — Horizontal bar chart of most-triggered policy rules

An optional time-series line chart renders when timestamp data is available. Filters (Decision, Risk Level, Component, Source) apply to the event records table but not to the charts.

Security Evaluation Lab (v1.1)

An expanded test suite of 60 controlled scenarios (T-01 through T-60) is run against unified_policy_check() at button-click time. Each scenario specifies a unique ID, a named category, the component context, the prompt or action, and the expected decision. The actual decision comes from the live policy engine — nothing is hardcoded.

CategoryTestsExpected Decision
BENIGN — Legitimate requests18ALLOW
INJECT — Prompt injection & jailbreak12FLAG / BLOCK

The lab now reports the following metrics, all computed from actual engine decisions:

  • Total tests, correct classifications, incorrect classifications, pass rate
  • False-positive count — benign requests incorrectly flagged or blocked by the engine
  • False-negative count — malicious/risky requests that were allowed through
  • Category breakdown table — pass %, FP count, and FN count per security category

Test cards are grouped by category in collapsible expanders. Results are stored in session_state.eval_lab_results and are not added to the main security event log.

Section 12

Request Flow through the Policy Engine

Every interactive evaluation (Playground, Sentinel, Data Transfer Check) passes through unified_policy_check(), which orchestrates three sequential steps:

1
ShadowAI Sentinel — Sensitive Data Scan Runs detect_sensitive_data() on the raw input. If sensitive data is found, the description is redacted, the decision is escalated to at least FLAG / MEDIUM, and a Sentinel rule entry is added.
2
Core Security Engine — Rule Evaluation Runs evaluate_security_event() on the redacted copy. Rules C, E, G, D, B are evaluated in priority order. The highest-priority triggered rule sets the decision. If no rule fires, Rule A or Rule F (ALLOW) is returned.
3
TrustGraph Heuristic Check Scans the description for references to RESTRICTED or UNTRUSTED node names. If a match is found, a TrustGraph finding is added and the decision is escalated to at least FLAG / MEDIUM.
4
Result + Logging Returns a dict: decision, risk_level, rules[], explanation, sensitive_scan, timestamp. log_event() appends the redacted result to session_state.security_log with deduplication.
Section 13

Current Limitations

The following limitations are inherent to the current prototype scope and are acknowledged in the project design.
AreaLimitation
Detection methodRule-based keyword and regex matching only. Cannot understand semantics, context, or obfuscated/encoded attacks.
False positivesOrdinary text that happens to match a regex pattern will be flagged.
False negativesSensitive data in formats not covered by the current six patterns will not be detected.
No real AI modelAll chatbot and agent interactions are entirely simulated. No LLM is integrated.
No persistenceAll data is stored in Streamlit session state and is lost when the browser tab is closed or the server restarts.
Fictional data onlyAll events, users, and resources are fictional demonstration data.
Single-file codebaseapp.py will need to be split into modules as the project grows.
Trust GraphThe graph is a static demonstration model; it does not discover real system components dynamically.
No authenticationThere is no user authentication or multi-user session support.
Section 14

Future Improvements

  • Real LLM Integration — Connect to an AI model (e.g. via IBM watsonx, OpenAI, or Hugging Face API) to provide a working chatbot alongside the security layer.
  • Persistent Storage — Replace session state with a SQLite or PostgreSQL database for durable event logs.
  • ML-Based Anomaly Detection — Complement the rule engine with machine-learning models capable of detecting semantic-level attacks.
  • Configurable Policy Rules — Allow operators to add, edit, and disable policy rules through the dashboard UI without modifying code.
  • Dynamic Trust Graph — Make the graph editable and able to discover real component relationships from a configuration file or service registry.
  • User Authentication & RBAC — Add login, multi-user session support, and role-based access control for the dashboard.
  • Agent Framework Integration — Connect to real agent frameworks (LangChain, AutoGen, IBM Bee Agent) via a middleware interception layer.
  • Export & SIEM Integration — Export event logs to CSV, JSON, or SIEM-compatible formats (CEF, LEEF) for enterprise monitoring pipelines.
  • Modular Codebase — Refactor app.py into separate Python modules (engine, sentinel, trustgraph, pages) for maintainability.
Section 15

Conclusion

AegisAI successfully demonstrates that a practical, lightweight security layer can be built on top of AI chatbot and agent interactions without requiring a live AI model. By combining a priority-ordered rule engine, regex-based sensitive data detection, a trust-graph model of component relationships, and a unified analytics dashboard, the project addresses several of the most pressing real-world AI security concerns.

The prototype establishes a working architecture — Scan → Evaluate → Log → Visualise — that scales naturally toward a production system. The clear separation between the policy engine, the Sentinel scanner, and the TrustGraph model means each layer can be independently enhanced or replaced as the project matures.

As a teaching and demonstration tool, AegisAI provides a tangible, interactive reference for AI security concepts: showing not just that threats exist, but how detection and enforcement logic can be practically implemented and surfaced to security operators.
